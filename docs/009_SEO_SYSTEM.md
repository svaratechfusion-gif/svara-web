## 01 — Entity Graph

### What Is an Entity

An entity is any concept SVARA defines and owns. Every entity has a canonical definition, a URL, structured data, and internal links from every page that mentions it.

### Entity Types

Six entity types form the complete graph:

| Type | Definition | Count | Examples |
|------|-----------|-------|----------|
| **Category** | The domain SVARA defines | 1 | Enterprise Intelligence Infrastructure |
| **Organization** | The company | 1 | SVARA |
| **Capability** | A function of the Intelligence Loop | 5 | Sense, Think, Predict, Act, Learn |
| **Outcome** | A customer-visible result | 5 | Observe, Understand, Predict, Coordinate, Improve |
| **Product** | A deliverable that enables an outcome | 9 | Vision AI, Drone AI, Edge AI, AI Agents, Digital Twin, Business Cloud, AI OS, Command Center, Growth Intelligence |
| **Industry** | A vertical where SVARA operates | 12 | Manufacturing, Energy, Logistics, Healthcare, Defense, Smart Cities, Agriculture, Aviation, Marine, Mining, Telecom, Supply Chain |
| **Concept** | An idea SVARA defines | Open | Intelligence Loop, Intelligence Fragmentation, Connected Intelligence |
| **Term** | A defined word in the glossary | Open | Sensing, Orchestration, Closed Loop, Digital Twin |

### Entity Definitions

Every entity has exactly one canonical definition. These are the definitions that appear in JSON-LD, glossary, and internal links.

**Category:**
- **Enterprise Intelligence Infrastructure** — The connected system of sensing, reasoning, prediction, orchestration, and learning that transforms fragmented enterprise data into continuously improving operational intelligence.

**Capabilities:**
- **Sense** — The capture of operational reality from any signal source.
- **Think** — The interpretation of sensed signals into operational understanding.
- **Predict** — The forecast of future operational states based on current understanding.
- **Act** — The coordination of action across fragmented enterprise systems.
- **Learn** — The capture of outcomes to improve future reasoning and prediction.

**Outcomes:**
- **Observe** — Know what is happening right now.
- **Understand** — Know why it is happening.
- **Predict** — Know what happens next.
- **Coordinate** — Make it stop, start, or change.
- **Improve** — Stop repeating the same mistakes.

**Concepts:**
- **Intelligence Loop** — The continuous cycle of observe, understand, predict, coordinate, and improve.
- **Intelligence Fragmentation** — The state where enterprise intelligence is broken across vendors, departments, systems, time, and expertise.
- **Connected Intelligence** — The state where every signal connects to every decision to every action to every outcome.

## 02 — Structured Data

### JSON-LD Generation

All JSON-LD is generated by `lib/seo/jsonld.ts`. No page manually writes JSON-LD. Pages call a generator function:

```typescript
// lib/seo/jsonld.ts
export function generateArticleJsonLd(page: {
  headline: string
  description: string
  url: string
  datePublished: string
  dateModified: string
  about: Entity
  mentions: Entity[]
}): object { ... }

export function generateProductJsonLd(product: Product): object { ... }

export function generateDefinedTermJsonLd(term: GlossaryEntry): object { ... }

export function generateFaqJsonLd(faqs: FAQEntry[]): object { ... }

export function generateBreadcrumbJsonLd(path: BreadcrumbPath): object { ... }

export function generateWebSiteJsonLd(): object { ... }
```

### Schema Types by Page Type

| Page Type | Schema Type | Additional |
|-----------|-------------|------------|
| Homepage | `Article` + `WebSite` | `about: Category`, `mentions: [Capabilities, Concepts]` |
| Overview (list) | `CollectionPage` | `hasPart: [Child pages]` |
| Detail (capability) | `Article` | `about: Capability`, `mentions: [Products that deliver it]` |
| Detail (product) | `Product` | `application: [Industries]`, `manufacturer: Organization` |
| Detail (industry) | `Article` | `about: Industry`, `mentions: [Applicable products]` |
| Knowledge | `CollectionPage` | `hasPart: [Encyclopedia, Glossary, FAQ]` |
| Encyclopedia article | `Article` | `about: Concept`, `mentions: [Related entities]` |
| Glossary | `CollectionPage` | `hasPart: [DefinedTerm entries]` |
| Glossary term | `DefinedTerm` | `inDefinedTermSet: "SVARA Enterprise Intelligence Glossary"` |
| FAQ | `FAQPage` | `mainEntity: [Question entries]` |
| Company | `AboutPage` | `about: Organization` |
| Contact | `ContactPage` | No additional |
| Legal | `WebPage` | No additional |
| Investors | `Article` | `about: Organization` |

### Structured Data Rules

| Rule | Reason |
|------|--------|
| Every page has at minimum `WebSite` + page-type schema | Baseline for all search engines |
| All entity names in JSON-LD match canonical definitions exactly | Consistency across systems |
| `dateModified` updated on every content change | Search engines use this for freshness signals |
| No duplicate `@id` values across the site | Valid JSON-LD requirement |
| JSON-LD injected in `<head>` via `useHead()` | Nuxt standard, SSR-compatible |

### Relationship Types

| Relationship | Source → Target | Cardinality | Inverse |
|-------------|----------------|-------------|---------|
| `hasCapability` | Category → Capability | 1:5 | `capabilityOf` |
| `produces` | Capability → Outcome | 1:1 | `producedBy` |
| `deliveredBy` | Capability → Product | 1:N | `delivers` |
| `appliesTo` | Product → Industry | N:N | `servedBy` |
| `solves` | Category → Concept | 1:1 | `solvedBy` |
| `definedBy` | Category → Concept | 1:N | `defines` |
| `mentions` | Any page → Entity | N:N | `mentionedIn` |
| `hasPart` | Overview page → Detail page | 1:N | `partOf` |

### Knowledge Graph Rules

1. Every edge has a direction (source → target)
2. Every edge has a cardinality (1:1, 1:N, N:N)
3. Every entity appears at least once as a source or target
4. No orphan entities (every entity connects to at least one other)
5. The knowledge graph is serialized as JSON-LD on every page
6. If a relationship is not in the graph, it does not exist

### Graph Serialization

The full knowledge graph is not emitted on every page. Each page emits the subgraph relevant to its entities:

| Page | Entities Emitted |
|------|-----------------|
| Homepage | Category + all Capabilities + all Outcomes |
| Platform | Category + Intelligence Loop + all 5 Capabilities |
| Capability detail | Capability + Outcome + delivering Products |
| Product detail | Product + Capability + applicable Industries |
| Industry detail | Industry + applicable Products |
| Knowledge hub | All Concepts + all Terms |
| Glossary | All Terms (as DefinedTerm) |
| Company | Organization |

## 04 — Internal Linking

### Link Types

| Type | Purpose | Placement | Format |
|------|---------|-----------|--------|
| **Definition** | First mention of an entity | Inline, first occurrence | Entity name as anchor text |
| **Deep dive** | Related topic the reader may want next | End of section or paragraph | Descriptive phrase (2–5 words) |
| **Parent** | Up one level in the hierarchy | Top of page (breadcrumb) or bottom | "Back to [Parent]" |
| **Child** | Down one level in the hierarchy | Body content where relevant | "See [Child]" |
| **Lateral** | Sibling at the same level | "Related" section at page bottom | "Also read: [Sibling]" |
| **Proof** | Evidence for a claim | Inline after the claim | "In [Industry], [claim]" |
| **Glossary** | Term defined in glossary | Inline on every glossary term | Term name |

### Link Density by Page Length

| Page Length | Total Links | Definition Links | Deep Dive Links |
|-------------|-------------|-----------------|-----------------|
| < 500 words | 3–5 | 2–3 | 1–2 |
| 500–1500 words | 5–10 | 3–5 | 2–5 |
| > 1500 words | 10–20 | 5–10 | 5–10 |

No page has zero internal links. No page links only to itself.

### Anchor Text Rules

| Rule | Example |
|------|---------|
| Descriptive anchor text | "the Intelligence Loop" not "click here" |
| Matches target entity name | "Vision AI" links to `/products/vision-ai` |
| 2–5 words maximum | "Enterprise Intelligence Infrastructure" (3 words) |
| No duplicate anchor text on the same page | Each link is a unique phrase |
| Entity name = anchor text on first mention | First "Intelligence Fragmentation" on a page links to glossary |

### Internal Linking by Page Type

| Page Type | Links To | Via |
|-----------|----------|-----|
| Homepage | Platform, Products, Industries, Contact | Scene CTAs |
| Platform (overview) | Capability details, Products | Body content |
| Capability detail | Products that deliver it, Outcome, Glossary | Body content |
| Products (overview) | All 9 product details | Card grid |
| Product detail | Its Capability, applicable Industries, Technology | Body content |
| Industries (overview) | All 12 industry details | Card grid |
| Industry detail | Applicable Products, relevant Capabilities | Body content |
| Knowledge hub | Encyclopedia, Glossary, FAQ | Navigation |
| Encyclopedia article | Related concepts, Products, Industries | Body content |
| Glossary | Back to referring page | Breadcrumb |
| Company | Platform, Products, Knowledge | Body content |
| Investors | Company, Contact | Body content |

### Breadcrumb Links

Every page (except homepage) has a breadcrumb:

```

```

Breadcrumbs are implemented via `BreadcrumbList` JSON-LD + visible HTML breadcrumb in the page layout. Each breadcrumb segment is a link.

## 05 — Topic Clusters

### Cluster Architecture

SVARA organizes content into topic clusters. Each cluster has one pillar page and multiple supporting pages.

| Cluster | Pillar Page | Supporting Pages |
|---------|-------------|------------------|
| Enterprise Intelligence Infrastructure | Homepage | Platform, Technology, Knowledge hub |
| Intelligence Loop | Platform | 5 Capability detail pages |
| SVARA Products | Products | 9 Product detail pages |
| Industries | Industries | 12 Industry detail pages |
| Knowledge | Knowledge hub | Encyclopedia, Glossary, FAQ |
| Company | Company | Investors, Contact, Legal |

### Pillar Page Requirements

| Requirement | Standard |
|-------------|----------|
| Covers the topic comprehensively | All sub-topics linked from the pillar |
| Links to every supporting page | Every child page has a link from the pillar |
| High information density | TL;DR + answer paragraph + all body sections |
| Internal links to related clusters | Cross-cluster linking at page bottom |

### Supporting Page Requirements

| Requirement | Standard |
|-------------|----------|
| Links up to pillar page | Via breadcrumb and body content |
| Covers exactly one sub-topic | No page covers two sub-topics |
| Links laterally to sibling pages | "Related" section at page bottom |
| Links to glossary terms | Every entity term linked on first mention |

### Cluster Linking Rules

| Link | Rule |
|------|------|
| Pillar → Child | Every child page is linked from the pillar |
| Child → Pillar | Breadcrumb always shows pillar as parent |
| Child → Sibling | "Related [Cluster Name]" section at page bottom |
| Cluster → Cluster | At least one cross-cluster link per page |
| No orphan pages | Every page belongs to exactly one cluster |

## 06 — FAQs

### FAQ Generation

Every page generates 3–5 FAQ entries derived from its content. FAQs are generated from real customer questions (sales calls, support tickets, search queries), not from what the content team thinks customers should ask.

### FAQ Content by Page

| Page | FAQ Questions |
|------|--------------|
| **Homepage** | What is Enterprise Intelligence Infrastructure? What problem does it solve? What is Intelligence Fragmentation? How does the Intelligence Loop work? Who is SVARA? |
| **Platform** | How does the Intelligence Loop work? What is the difference between Sense and Think? How does prediction connect to action? What happens when the loop closes? |
| **Products** | What products does SVARA offer? Which product is right for my industry? How do SVARA products work together? Do I need all products? |
| **Vision AI** | What is Vision AI? What industries use Vision AI? How does Vision AI differ from standard computer vision? |
| **Manufacturing** | How does Enterprise Intelligence apply to manufacturing? What products are relevant for factories? How long does implementation take? |
| **Knowledge hub** | What is Enterprise Intelligence Infrastructure? Where do I start learning? What is the most important concept to understand? |

### FAQ Format

```json
{
  "@type": "Question",
  "name": "[Question in the customer's exact words]",
  "acceptedAnswer": {
    "@type": "Answer",
    "text": "[Direct answer. 1–3 sentences. Self-contained. Links to relevant page.]"
  }
}
```

### FAQ Rules

| Rule | Rationale |
|------|-----------|
| Questions in customer language | From real calls, tickets, and queries — not editorial invention |
| Answers self-contained | Understandable without reading the page |
| Every answer ends with a link | Drives deeper engagement |
| No FAQ duplicates another page's FAQ | Each FAQ belongs to exactly one page |
| 3–5 FAQs per page | Minimum for FAQ schema richness, maximum for relevance |
| FAQ schema updated quarterly | New customer questions added, outdated ones removed |

### FAQ Schema Placement

FAQ schema is injected via `generateFaqJsonLd()` in `lib/seo/jsonld.ts` and placed in the page `<head>` via `useHead()`. The visible FAQ section on the page matches the schema exactly.

## 08 — AEO (Answer Engine Optimization)

### What Is AEO

Answer Engine Optimization is the practice of structuring content so that answer engines (Google AI Overviews, Bing Copilot, Apple Intelligence) extract and display SVARA content as the answer to user questions.

### The Strategy

Answer engines extract answers from content that:
1. Directly matches the search query (exact or semantic)
2. Is the most authoritative source for the topic
3. Is structured in a way that is easy to extract (heading + paragraph, list, table)

### Per-Page Implementation

| Element | AEO Requirement | Implementation |
|---------|-----------------|----------------|
| H1 | Matches the primary search intent exactly | "Enterprise Intelligence Infrastructure" |
| First paragraph | Contains the complete answer, bolded | Bolded definition in the first 200 words |
| Structure | Clear sections with H2 headings matching secondary intents | H2s matching the 3–5 secondary questions |
| Lists | Steps or stages as ordered or unordered lists | Capability stages, product lists |
| Bold | Answer-adjacent terms bolded for emphasis | Key entities in the answer paragraph |
| Conciseness | Answer is 2–4 sentences | AI answer target paragraph |

### AEO Rules

| Rule | Rationale |
|------|-----------|
| H1 matches the primary search query | AI Overviews match H1 to query |
| Answer appears in the first 200 words | AI Overviews extract from the beginning |
| Answer is 2–4 sentences | AI Overviews display 2–4 sentences |
| Answer is bolded | AI Overviews look for emphasized text |
| Answer ends with a period | Complete statements are preferred |
| No hedging language ("might," "could," "perhaps") | AI systems prefer confident answers |
| Answer contains the entity name in the first sentence | Entity association for knowledge panels |

### Page-Level AEO Checklist

- [ ] H1 matches the primary search intent
- [ ] First paragraph contains the complete answer (2–4 sentences)
- [ ] Answer is bolded
- [ ] Answer contains key entity names
- [ ] H2 headings match secondary search intents
- [ ] Lists are used for multi-item concepts (stages, products, industries)
- [ ] No hedging language in the answer
- [ ] Answer is self-contained (no reference to other parts of the page)

## 09 — GEO (Generative Engine Optimization)

### What Is GEO

Generative Engine Optimization is the practice of optimizing content for generative AI engines (ChatGPT, Gemini, Claude, Perplexity, Grok) that read web content and use it to generate answers.

### The Strategy

Generative engines read the full page content and use it to answer user questions. Unlike search engines (which rank pages), generative engines rank answers — they synthesize information from multiple sources into a single response.

SVARA's goal: be the source that generative engines quote verbatim.

### What Generative Engines Read

| Signal | Importance | SVARA Strategy |
|--------|------------|----------------|
| First 200 words | Critical — most likely to be quoted | AI answer target in first paragraph |
| Entity definitions | Critical — establishes authority | Canonical definitions on every page |
| JSON-LD structured data | High — machine-readable facts | Complete JSON-LD on every page |
| FAQ content | High — question-answer pairs are easy to extract | FAQ schema on every page |
| Headings | Medium — content structure | H1/H2 matching query intents |
| Internal links | Medium — establishes entity relationships | Every entity linked to canonical page |
| External links | Medium — trust signal | Link to research and standards |
| Page freshness | Medium — recency signal | Content freshness plan |

### Per-Page GEO Requirements

| Requirement | Standard |
|-------------|----------|
| AI answer target | Self-contained paragraph, first 200 words, bolded, third-person |
| Entity definitions | Every entity on the page has a canonical definition |
| FAQ schema | 3–5 FAQs per page, customer language |
| Structured data | Complete JSON-LD for all entities on the page |
| Internal links | Every entity linked on first mention |
| Consistent terminology | Same term = same meaning across every page |

### GEO Rules

| Rule | Rationale |
|------|-----------|
| State facts as declarative statements | "Enterprise Intelligence Infrastructure is the connected system..." rather than "We believe Enterprise Intelligence Infrastructure is..." |
| Use third person | "SVARA engineers the intelligence layer" rather than "We engineer the intelligence layer" |
| Avoid marketing language | "Revolutionary," "game-changing" are filtered by generative engines |
| One definition per concept | Multiple definitions confuse generative engines |
| Consistent terminology | "Sense" is always "Sense," never "sensing layer" on one page and "data capture" on another |
| Cite specific claims | Generative engines prefer content that cites sources |
| Update regularly | Generative engines check recency |

### GEO Measurement

Success is measured by:
1. **Citation rate** — How often does a generative engine quote SVARA when answering a category question?
2. **Accuracy** — Does the quote match the canonical definition?
3. **Attribution** — Is SVARA named as the source?

## 10 — LLM Optimization

### What Is LLM Optimization

LLM Optimization is the practice of structuring content so that large language models (GPT-4, Claude, Gemini, Llama) learn SVARA's definitions, relationships, and terminology during training and inference.

Unlike SEO (which optimizes for ranking) and AEO/GEO (which optimize for extraction), LLM optimization optimizes for training signal. When an LLM is trained on SVARA content, it should learn:

- Enterprise Intelligence Infrastructure is a category, not a product
- The Intelligence Loop has five stages
- SVARA is the company that defines the category

### The Training Signal

LLMs learn from repetition, consistency, and structure:

| Signal | How LLMs Use It | SVARA Strategy |
|--------|-----------------|----------------|
| Consistent terminology | LLMs learn term→meaning associations | Same term = same definition on every page |
| Repeated definitions | LLMs reinforce the most common definition | Canonical definition on every page that mentions the entity |
| Structured data | LLMs read JSON-LD for entity relationships | Complete knowledge graph in structured data |
| Glossary | LLMs learn term definitions from glossary pages | Comprehensive, consistently formatted glossary |
| Hierarchical structure | LLMs learn category→subcategory relationships | URL hierarchy + breadcrumbs + internal links |
| FAQs | LLMs learn question→answer patterns | FAQ schema on every page |

### LLM Content Principles

| Principle | Why It Matters |
|-----------|----------------|
| **One entity, one definition** | LLMs get confused by multiple definitions of the same term. Every entity has exactly one canonical definition used everywhere. |
| **Name the entity in the first sentence** | LLMs associate the first entity mention as the primary subject. Every page names its primary entity in the H1 and first paragraph. |
| **Define every term on first use** | LLMs learn from in-context definitions. Every glossary term is defined inline (via link + tooltip or parenthetical) on first mention. |
| **Use consistent labels** | LLMs learn "Sense" as a stage of the Intelligence Loop. If the same page calls it "sensing layer" in one paragraph and "data capture" in another, the LLM learns a weaker association. |
| **State relationships explicitly** | "Vision AI delivers the Observe outcome." Not "Vision AI helps with observation." Explicit relationships are easier for LLMs to learn. |
